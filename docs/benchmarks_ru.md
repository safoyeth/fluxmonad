# Бенчмарки производительности FluxMonad

**[English](benchmarks.md)** | **[Русский](benchmarks_ru.md)**

В данном документе приведены результаты замеров производительности на **1 000 000 записей**, сравнивающие FluxMonad со стандартными потоковыми конвейерами на базе генераторов Python (`itertools`).

Скрипт бенчмарка: [`benchmarks/benchmarks.py`](file:///home/safoyeth/Документы/fluxmonad/benchmarks/benchmarks.py)  
Инструменты телеметрии: модуль `tracemalloc` (отслеживание пикового потребления RAM) и `time.perf_counter`.

---

## 1. Сводные результаты бенчмарков

| Сценарий | Чистый Python / `itertools` | FluxMonad | Использование памяти | Сравнение |
| :--- | :--- | :--- | :--- | :--- |
| **1. Stream ETL + Early Cutoff** <br> `Filter -> Map -> Take(10k)` | 0.1065 с | 0.1596 с | 2.60 МБ vs 2.62 МБ | Сопоставимая скорость при полной инкапсуляции |
| **2. Heavy Projection + Filter** <br> `Extend -> When(Predicate)` | 0.8852 с | **0.4065 с** | 2.91 МБ vs 2.90 МБ | **⚡ На 54.1% быстрее** (благодаря Predicate Pushdown) |
| **3. Full Stream Reduction** <br> `Sum по 1 000 000 строк` | 2.7208 с | 2.8061 с | 0.00 МБ vs 0.01 МБ | Нулевое удержание памяти ($O(1)$ пиковый RAM) |

## 2. Подробный анализ сценариев

### Сценарий 1: Потоковый ETL с ранней остановкой (`Take(10 000)`)
- **Цель**: Проверить, что ленивые вычисления не потребляют и не удерживают лишние записи после границы отсечения.
- **Пайплайн**: 1 000 000 записей $\to$ Фильтрация по `age >= 18` и `status == "active"` $\to$ Вычисление нормализованного скора $\to$ `take(10_000)`.
- **Вывод**: И `itertools`, и `FluxMonad` вычисляются строго лениво, останавливая чтение сразу же после 10 000-й записи. Расход памяти строго ограничен объемом результирующего буфера (~2.6 МБ).

### Сценарий 2: Тяжелая проекция и проталкивание предикатов
- **Цель**: Измерить экономию процессорного времени, когда ресурсоемкое вычисление расположено перед независимым фильтром.
- **Операция**:
  ```python
  Flux(stream)
      .extend("token", heavy_hash_computation)
      .when(Field("age") >= 90)  # Отбрасывает 90% записей
      .to_list()
  ```
- **Чистый Python**: Наивно рассчитывает `heavy_hash_computation` для 100% записей (100 000 вызовов) до отсечения 90% в фильтре $\to$ **0.8852 с**.
- **FluxMonad**: Оптимизатор RBO определяет, что предикат зависит исключительно от поля `age`, и перемещает фильтр перед `extend()`. Тяжелая функция `heavy_hash_computation` вызывается только для 10% записей $\to$ **0.4065 с (сокращение времени на 54.1%)**.

### Сценарий 3: Агрегация потока из 1 000 000 строк
- **Цель**: Оценить пропускную способность и стабильность работы сборщика мусора при полной редукции потока.
- **Вывод**: Вычисление `Flux.sum()` по 1 000 000 записей выполняется за 2.80 с практически без аллокаций в куче (дельта пиковой памяти ~0.01 МБ), подтверждая потоковую обработку с константной памятью.
